# Card onboarding design (issuer registers a card, member adds it to a wallet)

Status: active temporary design artifact (see `.agents/rules/superpowers-policy.md`).
Written in autonomous mode: every decision below was made by the agent and is
flagged for the user in the hand-off. Reference material: the two mockups
`store-onboarding.html` / `onboarding.html` in the staff repo and its earlier
dash implementation, used for behaviour only; all code here is written from
scratch (AGENTS.md).

## Goal

Make this workflow work end to end on the fake chain and, with secrets, live:

1. An operator opens `dash.fuda.sh`, signs in with a passkey, designs a card
   (handle, venue name, tagline, card title, brand colour, card type, perk,
   reward, expiry, lock-screen relevance) with a live preview, and publishes it.
   The publish screen shows the QR and link `https://fuda.sh/@<handle>`.
2. A member opens `fuda.sh/@<handle>` (redirected to `app.fuda.sh/@<handle>`),
   taps "Get your free membership card", receives a `standard` (Bearer) right
   issued in one tap, and adds it to Apple Wallet, Google Wallet, or keeps the
   browser pass. The pass carries the venue name, card title, brand colour and
   member number.

This is the self-serve handle route that `docs/specs/pass-types-and-flows.md`
§U1 describes as the product model but marks as not implemented.

## Decisions

1. **Operator sign-in = Base Account passkey + message signature.**
   `POST /auth/challenge { address }` → `{ nonce, message }`;
   `POST /auth/verify { address, nonce, signature }` → `{ token, issuer | null }`;
   `POST /auth/logout`. The api verifies with `ChainClient.verifyMessage`
   (EOA, ERC-1271, ERC-6492 — a Base Account is an undeployed smart account on
   first use), so the in-memory fake chain covers it. Sessions live 30 days;
   only the SHA-256 of the token is stored. Base Account keeps WebAuthn on its
   own origin, so `dash.fuda.sh` needs no `rp.id`. The admin token stays for the
   existing admin routes; it is not an operator identity and cannot create an
   issuer. `sessions.issuer_id` is filled at verify time from
   `issuers.operator_address`, so a returning operator lands on their card.
2. **Data model.** `issuers` (id, handle UNIQUE, name, tagline, brand_color,
   operator_address UNIQUE, created_at), `cards` (id, issuer_id, title,
   category `membership|ticket`, perk, reward, validity_days NULL, lock_screen
   0/1, venue_lat, venue_lng, created_at), `sessions` (token_hash PK, address,
   issuer_id NULL, created_at, expires_at), and `members.card_id` NULL. One
   issuer per operator address in this slice; issuer → cards is 1:N so a second
   card is a later, additive change. `issuers` is a product/branding entity:
   every attestation still comes from the fuda signer under `DELEGATION_UID`.
   Per-issuer IssuerDelegation and `ens_names.kind='issuer'` rows are out of
   scope.
3. **Handle rule** is the ENS issuer-label rule already in
   `apps/api/src/ens/names.ts` (lowercase `[a-z0-9-]`, 1–63, no edge hyphen,
   reserved words). It moves to `@fuda/sdk` (`isIssuerHandle`,
   `RESERVED_ISSUER_HANDLES`) so dash validates client-side and the api enforces
   the same rule; the reserved set gains the api route prefixes (`auth`,
   `issuers`, `pass`, `verify`, `issue`, `members`, `revoke`, `challenge`,
   `health`, `ens`, `signed`, `private`, `rights`).
4. **Member number** is generated by the api for self-serve rights (13 chars,
   28-char alphabet, Luhn mod 28; `docs/specs/ens-naming.md#member-number`).
   Generator and formatter (`4-4-5` upper-cased display) live in `@fuda/sdk`
   next to the validator. It is stored in `members.member_id`; a partial unique
   index `(card_id, member_id) WHERE card_id IS NOT NULL` makes it unique per
   card, and the api re-draws on a collision before attesting. The Bearer
   holder nonce preimage is the bare member number (unchanged `bearerHolder`),
   so a future activation recomputes the address from the row alone.
5. **Self-serve issuance** is Bearer only: `POST /issuers/:handle/issue`
   (no body, `rateLimit({ budget: 20 })` per IP per hour) → tier 0,
   `usageModel` = `SINGLE_USE` for `ticket` else `MULTI_USE`, `validUntil` =
   now + `validity_days` days when set, else 0. Response:
   `{ uid, level: 'bearer', holder, qr, passUrls, memberNumber }`. Signed and
   +Private are not reachable from the handle route.
6. **Public card read**: `GET /issuers/:handle` →
   `{ handle, name, tagline, brandColor, card: { id, title, category, perk,
   reward, validityDays } }`, `404 not_found` otherwise, `cache-control:
   no-store`. `GET /issuers/check?handle=` is session-gated (no anonymous
   enumeration) → `{ handle, valid, available }`.
7. **Public URL** is built from a new `PUBLIC_BASE_URL` binding
   (`https://fuda.sh` in production, `http://localhost:5173` in `env.dev`),
   never from the request URL.
8. **Pass branding**: `@fuda/pass` inputs gain optional `issuerName`,
   `cardTitle`, `brandColor` (`#RRGGBB`), `memberNumber`; the web pass, the
   Google generic object and the Apple storeCard render them when present and
   keep today's output otherwise. `loadPassRow` joins `cards`/`issuers` through
   `members.card_id`. The +Private 404 path is untouched. Apple gets
   `locations` from the card's venue when `lock_screen` is set.
9. **Logo upload is deferred.** It needs an R2 binding, multipart handling and
   variant validation; the card preview and passes use name, title and colour.
10. **app `/@handle` route**: `routeFor` gains a `card` route for `/@<handle>`
    that, like `/signed`, must run on the app origin (the api's CORS list) and
    redirects there from the apex. The screen fetches the card, issues on tap,
    shows the member number, QR and the three pass actions, and remembers the
    issued right in the existing device pass memory plus a per-handle record so
    a revisit shows the same card instead of issuing twice. English only, as
    the app is today.
11. **dash routes** `/new` (designer) and `/published` (publish screen). The
    sign-in screen offers the passkey first and the admin token as a secondary
    path. Session state is a union: an admin-token session shows Overview /
    Rights / Issue; an operator session shows the card pages. Scoping the admin
    member list to an operator's card is a follow-up.

## Out of scope (follow-ups)

Logo upload; daily-operations screens (scan-and-stamp, activity, updates);
stamp/reward semantics beyond display text; operator-scoped `/members`; a
second card per issuer in the UI; Japanese copy in the member app; Google
pass `locations`.
