# World ID research notes — 2026-09-26

**Status: investigative notes, not a canonical spec.** `docs/integrations/` (currently `ens.md`,
`thegraph.md`) is this repository's home for *finished* integration documentation. The durable parts
of this file may later be folded into a `docs/integrations/world-id.md`; until then, nothing here is
authoritative for fuda's behaviour.

Scope: the seven questions raised by the Verified Human badge work. fuda's shape is assumed
throughout: a non-React web client on headless `@worldcoin/idkit-core@4.3.0`, **not** a World App
mini-app, a Cloudflare Worker signing with `@worldcoin/idkit-server@1.1.1`, the `orbLegacy` preset
with `allow_legacy_proofs: true`, and a unique index over `(verifier, scope, subject_key)` with
`subject_key` = nullifier and `scope` = `app_id:action`.

## Headline

**Only `production` can honestly claim human uniqueness.** `staging` credentials are "freely
mintable from the simulator" and the Portal's own schema restricts a "faux issuer (128)" for
`proof_of_human` to `staging`/`sandbox`. And as of a 2026-09-25 commit the production verify endpoint
**refuses** staging/sandbox proofs unless the app has opened a 24-hour staging window *and* sends an
`x-staging-verification-token` header — a requirement that appears in no published doc page.

**The uniqueness claim is sound.** The nullifier is derived from `(user, rp/app, action)` in both 3.0
and 4.0 and is stable. The `4-0-migration` "one-time-use" wording is about not reusing a nullifier as
a persistent cross-action identity, not about the value varying. Details in Q3.

## Q1. Environments and app review

### What the three environments are — **confirmed**

`production` | `staging` | `sandbox` select which World ID client the connect URL hands off to. The
installed WASM carries exactly three connect bases:

```
https://world.org/verify   https://staging.world.org/verify   https://sandbox.world.org/verify
```

— `strings` over `/home/yuji/code/github.com/oboroxyz/fuda-sh/node_modules/.pnpm/@worldcoin+idkit-core@4.3.0/node_modules/@worldcoin/idkit-core/dist/idkit_wasm_bg.wasm`
(the same file's enum strings are `production` `staging` `sandbox`). The TS default is `"production"`
— `dist/index.js` has `environment: config.environment ?? "production"` in all three request
builders.

- **staging = the simulator.** "To test during development, use the [simulator](https://simulator.worldcoin.org/) and set `environment` to `"staging"`." — <https://docs.world.org/world-id/idkit/integrate.md> (Step 4). And: "The **production** World ID app only signs **production** proofs. A **staging** action only verifies against the World ID **Simulator**. The IDKit `environment` prop, the action's `environment`, and the simulator-vs-real-app choice **must all match.**" — <https://docs.world.org/world-id/SKILL.md> (Phase 5).
- **sandbox = a separate, production-like backend with separate app builds** distributed via TestFlight / a private Play track. — <https://docs.world.org/world-id/sandbox/what-is-sandbox.md>, <https://docs.world.org/world-id/sandbox/sandbox-access.md>

### Are staging/sandbox proofs backed by real Orb verification? **No — confirmed**

This is the question that decides whether a non-production demo can claim anything.

- Sandbox, in World's own words: "**Simulated verification.** Exercise verification flows without real hardware or real-world credentials." and "**Not a source of real uniqueness.** Sandbox does not represent real-world identity or uniqueness at scale." — <https://docs.world.org/world-id/sandbox/what-is-sandbox.md>
- Staging, from the Portal source: "staging credentials are **freely mintable from the simulator**, the staging verifier contract accepts them … An ungated staging request therefore buys a fresh, distinct nullifier against a production RP and **defeats the one-person-one-nullifier guarantee** the endpoint exists to provide." — <https://raw.githubusercontent.com/worldcoin/developer-portal/main/web/api/v4/verify/staging-access.ts>
- The request schema gives away the mechanism: `supportedCredentialIssuers` maps `proof_of_human → 1`, and a second branch accepts `issuer_schema_id === 128` for `proof_of_human` only when the environment is `staging` or `sandbox`, with the comment "The **faux issuer (128)** is limited to staging." — <https://raw.githubusercontent.com/worldcoin/developer-portal/main/web/api/v4/verify/request-schema.ts>

**Consequence for the demo:** a badge earned in `staging` or `sandbox` proves nothing about
uniqueness. If the demo needs to assert "one human, one pass", it must run in `production` against
real World App users.

### New, undocumented gate: staging/sandbox proofs are refused by production verify — **confirmed in source, absent from docs**

`web/api/v4/verify/index.ts` normalises `sandbox → staging` for the verifier, then:

> `if (verifierEnvironment === "staging" && process.env.NEXT_PUBLIC_APP_ENV !== "staging") { … authorizeStagingVerification(…) }`

Two independent things must hold, "and neither of them is the client's word": (1) the app's team
opened a time-boxed staging window out of band, and (2) the request carries the token that opening
the window issued, as the `x-staging-verification-token` header. Window length is
`STAGING_VERIFICATION_WINDOW_MS = 24 * 60 * 60 * 1000`. Failure is **HTTP 403** with
`code: "environment_not_allowed"`.
— <https://raw.githubusercontent.com/worldcoin/developer-portal/main/web/api/v4/verify/index.ts>,
<https://raw.githubusercontent.com/worldcoin/developer-portal/main/web/api/v4/verify/staging-access.ts>

The window is opened with an MCP tool: `set_world_id_staging_verification` — "Open (or close) a 24h
window in which `/api/v4/verify` accepts staging / sandbox proofs, and issue the token those calls
must send as `x-staging-verification-token`", parameters `app_id`, `enabled`.
— <https://raw.githubusercontent.com/worldcoin/developer-portal/main/web/api/mcp/SKILL.md>

**Contradiction, documented deliberately.** The published sandbox page still says the opposite:

> "To verify a proof, send it to the production verify endpoint (`https://developer.world.org/api/v4/verify/${rp_id}`). **Nothing else is required** — the handoff will open the sandbox World ID app and return a proof to your session over the bridge."
> — <https://docs.world.org/world-id/sandbox/sandbox-access.md>

versus the staging-access source above. **The source is more likely current.** `staging-access.ts`
landed 2026-09-25 in commit *"fix(verify): bind v4 verification environment to the app (H1 #3989287)"*
— an externally reported security fix, one day before this research. The sandbox doc's last touch was
2026-09-02 (`docs(sandbox): update iOS access to the App Store Connect enrollment flow`). A
security-motivated tightening shipped 23 days after the doc was last edited is the change; the doc is
stale. *Caveat, and it matters:* being on `main` is not proof of being deployed to
`developer.world.org`. Whether the gate is live today is **Unknown**. Treat non-production
verification as liable to 403 at any moment.

Also note the published MCP reference page does **not** list `set_world_id_staging_verification`
(tool table at <https://docs.world.org/model-context-protocol/developer-portal.md> stops at
`create_world_id_action`), so the only description of the tool is in the repo.

### Does receiving production verifications require app review / store listing? **No — confirmed from the verify implementation; not stated either way in the docs**

The verify endpoint's only app-level gates are:

1. `resolveRpRegistration` resolves `app_id`/`rp_id` to an RP registration; not found → **400** `app_not_migrated` ("This app has not been migrated to World ID 4.0. Please use the v2 verify endpoint.")
2. `rpRegistration.status !== RpRegistrationStatus.Registered` → **400** `rp_not_active` ("RP registration is not active.")
3. `app.status !== "active" || app.is_archived || app.deleted_at` → **404** `not_found` ("App not found. App may be no longer active.")

There is **no** check of app review status, `is_verified`, store listing, or metadata completeness.
— <https://raw.githubusercontent.com/worldcoin/developer-portal/main/web/api/v4/verify/index.ts>

Supporting evidence that review is a *Mini App Store listing* concern, not a World ID one:

- The review guidelines open with "These guidelines dictate the rules for apps which seek to be **displayed to users from within World App**" and cover naming, showcase imagery, store description, and removal from the Mini App Store. — <https://docs.world.org/mini-apps/guidelines/policy>
- fuda is an `external` app, not `mini-app`: "`app_mode` is fixed at create time. Create a **new** app with the right mode (`external` for IDKit, `mini-app` for MiniKit)." — <https://docs.world.org/world-id/SKILL.md>
- The `/api/v1/precheck` example response carries `is_verified: false` alongside `can_user_verify: 'yes'` — a *verified app* badge is orthogonal to whether users can verify. — <https://docs.world.org/api-reference/developer-portal/get-action-metadata.md>

**What actually gates the demo** is on-chain RP registration, not review: "Poll
`get_world_id_registration_status` until the intended environment is `registered`. **Production must
be registered before launch.**" and the launch checklist item "On-chain registration polled to
`registered` … before launch." — <https://docs.world.org/world-id/SKILL.md>

*Practical read for the user mid-flow:* finishing "Basic information → Availability → Localised
content → Review and confirm" is **not** a prerequisite for production verifications. Confirming RP
registration is `registered` in `production` is. Note however that the MCP "build an external
(non-mini) World ID app end-to-end" flow does list `submit_app_for_review` as its last step — so the
Portal UI will keep nudging toward it. That is a listing step, not a verification step.

### Does the "Availability" setting affect which environment is used? **Not found in primary sources**

No doc page, OpenAPI schema, or Portal source read here connects an "Availability" app setting to the
`environment` used for verification. The environment is determined by (a) the `environment` field in
the IDKit request, which picks the connect base URL, and (b) the `environment` field in the verify
request body. `configure_mini_app`'s `supported_countries` / `supported_languages` are store-listing
availability, unrelated. Do not assume a link.

## Q2. RP registration and the signer address

### How an RP is registered and where `rp_id` comes from — **confirmed**

"Create your app in the [Developer Portal](https://developer.world.org). If you're migrating from an
old app, complete RP registration by clicking the **Enable World ID 4.0** banner. Keep these values:
`app_id`, `rp_id`, `signing_key` — this should be stored as a secret."
— <https://docs.world.org/world-id/idkit/integrate.md> (Step 2)

Via MCP: `configure_world_id { app_id }` — "Create a managed World ID 4.0 RP for the app: KMS manager
key, **on-chain registration**, signer wallet"; returns the private key exactly once.
— <https://raw.githubusercontent.com/worldcoin/developer-portal/main/web/api/mcp/SKILL.md>

`rp_id` is a `u64` rendered as `rp_{:016x}`: `impl fmt::Display for RpId { write!(f, "rp_{:016x}", self.0) }`
— <https://raw.githubusercontent.com/worldcoin/world-id-protocol/main/crates/primitives/src/rp.rs>

### Must the signer address be registered in the Portal? **Yes — confirmed**

The Portal exposes exactly that: `get_world_id_signing_key` — "**Fetch the current signer address.**
Private keys are not returned." — <https://docs.world.org/model-context-protocol/developer-portal.md>
(tool table). The registry side is what is checked: "World ID verifies the signature **before
generating a proof**." — <https://docs.world.org/world-id/idkit/signatures.md>

Rotation semantics: "rotation creates a new key and **invalidates the old signer**" and
`get_world_id_signing_key` "cannot recover" a lost private key.
— <https://docs.world.org/world-id/SKILL.md>

### What failure looks like — **confirmed, and it is *not* an HTTP status from verify**

This is the correction that matters. A missing, wrong, or unregistered signer **never reaches the
verify endpoint**, because the signature is checked before a proof exists. It surfaces client-side
from `pollUntilCompletion()` as `{ success: false, error: <code> }`:

| IDKit error code | Documented meaning | Typical cause |
| --- | --- | --- |
| `invalid_rp_signature` | "RP signature could not be verified." | wrong signing key, wrong signed message, action mismatch |
| `unknown_rp` | "RP is not known to the registry." | `rp_id` never registered on-chain |
| `inactive_rp` | "RP is registered but inactive." | registration not active in this environment |
| `rp_signature_expired` | "RP signature has expired." | TTL elapsed (default 300 s) |
| `timestamp_too_old` / `timestamp_too_far_in_future` | stale / skewed clock | Worker clock skew |
| `duplicate_nonce` | "RP reused a signature nonce." | nonce reuse across requests |
| `invalid_rp_id_format` | "RP ID is malformed." | not `rp_…` |

— <https://docs.world.org/world-id/idkit/error-codes.md>; the same set is the `IDKitErrorCodes` enum
in `node_modules/.pnpm/@worldcoin+idkit-core@4.3.0/node_modules/@worldcoin/idkit-core/dist/index.d.ts`.

The verify endpoint's *own* registration failures are the three listed in Q1: **400**
`app_not_migrated`, **400** `rp_not_active`, **404** `not_found`. Plus the documented gotcha
"`/api/v4/verify/{rp_id}` returns `not_registered` or 4xx with `rp` errors → On-chain registration is
still `pending`" — <https://docs.world.org/world-id/SKILL.md>.

**fuda implication:** a signer misconfiguration is a *client-visible IDKit error code*, not a verify
HTTP error. Surface those codes. "Relevant failures — replayed nullifiers, invalid action/signature,
or environment mismatch — produce an actionable user-facing error instead of an indefinite loading
state" is an explicit launch requirement. — <https://docs.world.org/world-id/SKILL.md>

### Signing algorithm, for reference — **confirmed, and the shipped types match the spec**

`msg = version(0x01) || nonce(32) || created_at_u64_be(8) || expires_at_u64_be(8) || action?(32)`
→ 49 bytes without action, 81 with. Signed EIP-191 over the *decimal* byte length, recoverable ECDSA
secp256k1, encoded `r || s || v` with `v = recovery_id + 27`. Action is `hash_to_field(utf8(action))`.
Uniqueness proofs include the action; session proofs omit it.
— <https://docs.world.org/world-id/idkit/signatures.md> (with test vectors), matching
`computeRpSignatureMessage`'s doc comment in
`node_modules/.pnpm/@worldcoin+idkit-server@1.1.1/node_modules/@worldcoin/idkit-server/dist/index.d.ts`.
The address-recovery inference in the package's own type docs is therefore correct.

## Q3. Nullifier stability — the load-bearing question

### Verdict

**The nullifier is stable for the same `(person, app/rp, action)` in both 3.0 and 4.0.** The
`4-0-migration` "one-time-use" wording does not mean the value varies between requests; it means the
protocol treats a second proof of the *same* action as a replay, and that a nullifier must not be
repurposed as a persistent cross-action user identifier. fuda's unique index over
`(verifier, scope, subject_key)` with `scope = app_id:action` is the right construction.

### The contradiction, quoted in full

**Stable (concepts):**

> "**Nullifier**: A component of the World ID ZKP; a unique identifier for a combination of a user, `app_id`, and `action`."
> — <https://docs.world.org/world-id/concepts.md>

**Stable, and more explicit (the current integration guide, Step 6):**

> "Every uniqueness proof contains a nullifier — a value derived from the user's World ID, your app, and the action. **The same person verifying the same action always produces the same nullifier**, but different apps or actions produce different ones, making nullifiers unlinkable across apps."
> — <https://docs.world.org/world-id/idkit/integrate.md>

**Apparently not stable (the 4.0 migration guide):**

> "In 3.0, many RPs treated nullifiers as persistent user identifiers. In 4.0, **nullifiers are one-time-use, and `session_id` is the stable link across requests.**"
> and, in its table: "Uniqueness proof | World ID 4.0: Nullifier still prevents proof reuse and is one-time-use. | What your backend should store: **Used nullifiers**."
> — <https://docs.world.org/world-id/4-0-migration.md>

### Why the stable reading wins — four independent pieces of evidence

1. **The protocol's own definition (4.0).** The authoritative Rust type:

   > "A nullifier is a unique, one-time identifier **derived from (user, rpId, action)** that lets RPs detect duplicate actions without learning who the user is."
   > — <https://raw.githubusercontent.com/worldcoin/world-id-protocol/main/crates/primitives/src/nullifier.rs>

   "Derived from (user, rpId, action)" is determinism, stated in the same sentence as "one-time".
   The two words describe different things: derivation is deterministic; *use* is once per action.
   The same file adds `as_number()` — "the **recommended way of enforcing nullifier uniqueness** …
   Store this number directly to enforce uniqueness."

2. **Sessions randomise the action *because* the nullifier is a function of it.** `SessionNullifier`
   is `{ nullifier, action }` where `action` must carry `OprfPrefix::SessionAction`, and:

   > "A session nullifier … **does NOT guarantee uniqueness of a World ID** as a `Nullifier` does. … This type exists as an adaptation to be able to use the same ZK-circuit for both Uniqueness Proofs and Session Proofs, and it encompasses: the nullifier used as the proof output, and **a random action bound to the same proof**."
   > — <https://raw.githubusercontent.com/worldcoin/world-id-protocol/main/crates/primitives/src/session.rs>

   Randomising the action to *destroy* linkability is only necessary if a fixed action *creates* it.
   (The nullifier is an OPRF output; `OprfModule::Nullifier` and the `Uniqueness = 0x00` /
   `SessionAction = 0x02` domain prefixes are in
   <https://raw.githubusercontent.com/worldcoin/world-id-protocol/main/crates/primitives/src/oprf.rs>.)

3. **`nullifier_replayed` would be meaningless otherwise.** "`nullifier_replayed` — Nullifier was
   already used for this action. Treat as an already-verified outcome; do not retry the same action as
   a new verification." — <https://docs.world.org/world-id/idkit/error-codes.md>. Per-nullifier replay
   detection presupposes a reproducible value.

4. **The Portal accepts a re-presented nullifier as success.** In the uniqueness handler, when the
   nullifier already exists: "Nullifier already exists — skip saving and return success", HTTP **200**,
   `message: "Proof verified successfully (nullifier reuse)"`.
   — <https://raw.githubusercontent.com/worldcoin/developer-portal/main/web/api/v4/verify/uniqueness-proof/handler.ts>

### 3.0 / legacy Orb proofs specifically — **confirmed stable, and scoped to `app_id`**

3.0 is Semaphore: the nullifier hash is bound to an *external nullifier* computed from `app_id` and
`action`.

> `externalNullifier = abi.encodePacked(abi.encodePacked(appId).hashToField(), action)`
> `externalNullifierHash = externalNullifier.hashToField();`
> — <https://docs.world.org/world-id/reference/contracts.md>

and the Portal reproduces exactly that when verifying a forwarded 3.0 proof:
`const externalNullifier = generateExternalNullifier(appId, action).digest;`
— <https://raw.githubusercontent.com/worldcoin/developer-portal/main/web/api/v4/verify/uniqueness-proof/verify-v3.ts>

The Create Action response also documents `external_nullifier` as "External nullifier **derived from
action and app_id**". — <https://docs.world.org/api-reference/developer-portal/create-incognito-action.md>

**So for `orbLegacy`, the scope really is `app_id` + `action`, not `rp_id` + `action`** — which makes
fuda's `scope = app_id:action` literally correct for the shipped preset. Note the 4.0 nullifier is
described as RP-scoped instead (`rpId`, and "RP-scoped nullifier (hex)" in the response types), so the
scope key's meaning silently changes if the preset ever moves to 4.0.

### Caveat worth designing around

Because a stable nullifier plus "one-time per action" means the protocol may refuse the *second*
attempt outright, a user who tries to badge twice is likelier to see IDKit `nullifier_replayed` than
to reach fuda's unique-index rejection. Both paths must produce the same user-facing "already
badged" outcome. "World ID 4.0 uniqueness proofs are **one-time per action for each user**. Use
separate actions for separate one-time operations, and sessions for recurring checks."
— <https://docs.world.org/world-id/SKILL.md>

Whether 3.0 legacy proofs are refused the same way at the World App layer is **Unknown** — the 3.0
model historically left deduplication to the RP ("your backend **must** check that the nullifier
hasn't been used before. Otherwise, the same person could verify multiple times for the same
action." — <https://docs.world.org/world-id/idkit/integrate.md>). Keep the DB index; it is the
defence that is documented as required.

## Q4. Legacy (`orbLegacy`) proof requirements

- **Portal-side enablement: none documented.** The only requirements stated for legacy presets are the request-level `allow_legacy_proofs: true` flag — "Required for request flows. Set to `true` while accepting World ID 3.0 fallback proofs" — and the preset itself. `orbLegacy` is listed plainly under "Other legacy presets" as "Orb verification." with no enablement note. Contrast with the two presets that *do* carry gates: `selfieCheckLegacy` — "Preview: Selfie Check is currently in preview. Contact us if you need it enabled." (in the shipped `.d.ts` and in the type docs) and `identityCheck` — "Identity Check is currently in preview. To use it or learn more, contact us." — <https://docs.world.org/world-id/idkit/credentials.md>. The absence of such a note for `orbLegacy` is the best available evidence; a positive statement "no enablement required" was **not found in primary sources**.
- **Quotas: none found** for legacy proofs specifically. See Q7.
- **Announced deprecation timeline: none — confirmed.** The migration guide explicitly refuses to give one: "Choose the transition and cutover dates for **your own rollout** rather than relying on a fixed global schedule." — <https://docs.world.org/world-id/4-0-migration.md>. A repository-wide grep of the full docs corpus (`https://docs.world.org/llms-full.txt`) for *deprecat / sunset / end of life / no longer supported / will stop* returns exactly one World ID hit: `deviceLegacy` — "**Deprecated.** Keep `deviceLegacy` only for existing Device integrations." `orbLegacy` is not deprecated.
- **The real restriction is user-side, not Portal-side.** `orbLegacy` "only returns World ID 3.0 proofs" (shipped `.d.ts`). A user who cannot mint a 3.0 proof fails with `world_id_3_not_available` — "World ID 3.0 credential is not available for that user", and such errors are **terminal**: "Retrying the same request usually returns the same result; change the requested credential policy or show a user-facing fallback instead." — <https://docs.world.org/world-id/idkit/error-codes.md>. **Whether every Orb-verified human can still produce a 3.0 proof today is Unknown** — no primary source read here states it either way. This is a live demo risk: a venue tester on a 4.0-only credential would hard-fail with a terminal error and no fallback.

## Q5. The v4 verify API

Endpoint: `POST https://developer.world.org/api/v4/verify/{rp_id}`. `rp_id` (`rp_…`) recommended;
`app_id` (`app_…`) still accepted for backward compatibility.
— <https://docs.world.org/api-reference/developer-portal/verify.md>

**Domain note:** the installed package's own README uses `https://developer.worldcoin.org/api/v4/verify/${RP_ID}`
(`node_modules/.pnpm/@worldcoin+idkit-core@4.3.0/node_modules/@worldcoin/idkit-core/README.md`), while
the docs and the OpenAPI `servers` list use `developer.world.org` as "Primary" and
`developer.worldcoin.org` as "**Legacy domain**". Not a contradiction — but the Worker should use
`developer.world.org`.

### Request body — forward the IDKit result verbatim

> "Forward the IDKit result payload as-is. **No field remapping is required.**" — <https://docs.world.org/world-id/idkit/integrate.md>
> "**DO NOT mutate, re-encode, or trim the proof JSON before forwarding** — pass exactly what IDKit returned." — <https://docs.world.org/world-id/SKILL.md>

For a 3.0 legacy proof the body is the `IDKitResultV3`: `protocol_version: "3.0"`, `nonce`, `action`,
`environment`, `responses[]` where each item requires `identifier`, `proof`, `merkle_root`,
`nullifier` and optionally carries `signal_hash` and `max_age`.
— <https://docs.world.org/api-reference/developer-portal/verify.md>

An undocumented request field exists in the implementation: `min_protocol_version`, the RP's own
floor, rejected with **400** `protocol_version_not_allowed` before any verification work.
— <https://raw.githubusercontent.com/worldcoin/developer-portal/main/web/api/v4/verify/index.ts>.
Not in the OpenAPI schema; treat as unsupported until documented.

### The nullifier field name — **confirmed: `nullifier`**

The implementation's guess is correct, at the top level *and* per result. Success response type:

```ts
type UniquenessProofSuccessResponse = {
  success: true;
  action: string;
  nullifier: string; // Hex format `0x` prefixed
  created_at?: string;
  environment: string;
  protocol_version: "3.0" | "4.0";
  results: UniquenessResult[];  // { identifier, success, nullifier?, code?, detail?, attribute? }
  message: string;
};
```

— <https://raw.githubusercontent.com/worldcoin/developer-portal/main/web/api/v4/verify/uniqueness-proof/handler.ts>,
matching the OpenAPI `VerifyV4SuccessResponse` (`success`, `action`, `nullifier`, `created_at`,
`environment`, `session_id`, `results`, `message`) at
<https://docs.world.org/api-reference/developer-portal/verify.md>. The top-level value is the
nullifier of the **first successful** result, normalised to `0x`-prefixed hex
(`normalizeNullifierHash`). The `protocol_version` echo is in the implementation but **not** in the
published OpenAPI schema — its carried comment is worth heeding: "Only 4.0 binds `nonce` as a circuit
public input, so a relying party that has migrated must check this to reject a proof it cannot bind
to a session."

Storage guidance, if fuda ever moves off a text column: "Nullifiers are returned as 0x-prefixed hex
strings representing 256-bit integers. **Convert and store them as numbers** to avoid parsing and
casing issues that can lead to security vulnerabilities." — <https://docs.world.org/world-id/idkit/integrate.md>
(`NUMERIC(78, 0)` in the PostgreSQL example). Same warning from the protocol: different strings may
represent the same field element, "which could result in a compromise of uniqueness"
(<https://raw.githubusercontent.com/worldcoin/world-id-protocol/main/crates/primitives/src/nullifier.rs>).
**With a text `subject_key`, normalise to lowercase 0x-padded-64 hex or to decimal before writing** —
the unique index is only as good as the canonicalisation.

### Success vs failure — both an HTTP status and a `success` boolean

| Status | Shape | When |
| --- | --- | --- |
| **200** | `{ success: true, action, nullifier, created_at?, environment, protocol_version, results[], message }` | at least one proof verified |
| **400** | `{ success: false, code, detail, results? }` | validation or verification failure |
| **403** | `{ success: false, code, detail }` | integrity-bundle failure, or `environment_not_allowed` |
| **404** | `{ success: false, code, detail }` | app not found / no longer active |

with `message: "Proof verified successfully (nullifier reuse)"`. **The Portal does not enforce
uniqueness for you** — "The Developer Portal confirms the proof is **cryptographically valid**, but
your backend must check that the nullifier hasn't been used before."

### Must `signal` be resupplied to verify? **No — confirmed**

The signal is carried inside the forwarded payload as `responses[].signal_hash`; there is no `signal`
field in any request schema. The Portal feeds `signal_hash: item.signal_hash` straight into the
sequencer call as a ZK public input for 3.0.
— <https://raw.githubusercontent.com/worldcoin/developer-portal/main/web/api/v4/verify/uniqueness-proof/verify-v3.ts>,
<https://docs.world.org/api-reference/developer-portal/verify.md>

Because it is *inside* the client-forwarded blob, "Your backend should enforce the same value"
(<https://docs.world.org/world-id/idkit/credentials.md>) — recompute `hashSignal(expected)` in the
Worker and compare, rather than trusting the forwarded `signal_hash`.

## Q6. `signal` and `signal_hash`

### Is it always present when a signal was supplied? **On fuda's path (bridge + 3.0): yes — confirmed. In general: no.**

This is the case where the shipped TypeScript and the source of truth disagree, so both are cited.

**Shipped `.d.ts` (optional):**

```ts
interface ResponseItemV3 {
  identifier: string;
  /** Signal hash (optional, included if signal was provided in request) */
  signal_hash?: string;
  …
}
```

— `node_modules/.pnpm/@worldcoin+idkit-core@4.3.0/node_modules/@worldcoin/idkit-core/dist/index.d.ts`

**Rust source of truth (required, for V3 only):** the same header in that file says "Result types —
re-exported from WASM bindings. Source of truth: `rust/core/src/wasm_bindings.rs`". In that source:

```rust
/// Protocol version 3.0 (World ID v3 - legacy format)
V3 {
    identifier: String,
    /// Signal hash (hash of the signal provided in the request, or hash of empty signal)
    signal_hash: String,
    …
}
```

— <https://raw.githubusercontent.com/worldcoin/idkit/main/rust/core/src/types.rs>

Note the divergence is structural, not cosmetic: every **V4** / session variant in that file declares
`signal_hash: Option<String>` with `#[serde(skip_serializing_if = "Option::is_none")]` — genuinely
omitted when no signal was requested. Only **V3** is non-optional. The `.d.ts` flattens all of them
to `signal_hash?: string`.

**Why V3 can't be missing on the bridge path.** The bridge does not return signal hashes at all;
IDKit reattaches them from the request:

```rust
// Search the `signal_hashes` or fallback to legacy signal hash for v3 responses
// since the bridge does not return signal hashes
let signal_hash = self.cached_signal_hashes
    .get(item.verification_level.as_ref())
    .unwrap_or_else(|| self.cached_signal_hashes.legacy());
item.into_response_item(signal_hash)
```

and `legacy()` is always a computed `String`:
`hash_signal(&Signal::from_string(params.legacy_signal.clone()))` — i.e. `hashSignal("")` when no
signal was given. `into_response_item(signal_hash: String)` then constructs `ResponseItem::V3` with a
non-optional field.
— <https://raw.githubusercontent.com/worldcoin/idkit/main/rust/core/src/bridge.rs>

**Verdict for fuda:** `orbLegacy` + bridge transport → `signal_hash` is always a populated string.
Failing closed on its absence will not reject a legitimate proof *on this path*.

### Could any legitimate flow omit it? **Yes — two, both outside fuda's current path**

1. **Any 4.0 response item without a signal.** `Option` + `skip_serializing_if` means the key is absent from the JSON. If fuda ever switches from `orbLegacy` to `proofOfHuman` (or accepts 4.0 fallback) *and* a request goes out without a signal, a valid proof arrives with no `signal_hash` and the current strictness rejects it.
2. **The World App native / mini-app transport for 3.0 — structurally nullable, probably fine in practice.** That conversion is hand-written JS, not WASM: `signal_hash: p.signal_hash ?? signalHashes[identifier] ?? signalHashes[incomingIdentifier] ?? legacySignalHash` — a `??` chain whose type permits `undefined`. — `…/@worldcoin/idkit-core/dist/index.js` (`nativeResultToIDKitResult`). In practice the last arm looks always populated: every `nativePayload*` variant writes `legacy_signal_hash` from `cached.legacy_signal_hash` (<https://raw.githubusercontent.com/worldcoin/idkit/main/rust/core/src/wasm_bindings.rs>), which is a non-`Option` `String` in `CachedSignalHashes` (<https://raw.githubusercontent.com/worldcoin/idkit/main/rust/core/src/bridge.rs>). **Not verified end-to-end on the native transport**, which fuda does not use. Flagging it only because the path becomes reachable the moment fuda is opened inside World App.

**The Portal itself tolerates absence**, which is the strongest argument that fail-closed is stricter
than the contract. Both the OpenAPI schema and the server-side validator supply defaults:

- v3: `signal_hash` default `0x00c5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a4` (= `hashSignal("")`)
- v4 / session: `signal_hash` default `0x0`

— <https://docs.world.org/api-reference/developer-portal/verify.md> (schema `default`s) and the yup
schema in <https://raw.githubusercontent.com/worldcoin/developer-portal/main/web/api/v4/verify/request-schema.ts>.

**Recommendation:** keep the check, but make it *conditional on having asked for a signal* rather than
unconditional — reject when a signal was requested and `signal_hash` is missing or does not equal the
locally recomputed `hashSignal(signal)`; accept absence only when no signal was requested. That keeps
the security property (the signal is what fuda expects) without the demo-breaking failure mode.

### How `hashSignal` is computed — **confirmed, two independent sources agree**

```
hash_to_field(input_bytes):
    h = keccak256(input_bytes)        # NOT SHA3-256 — different padding
    n = big_endian_uint256(h) >> 8    # shift right 8 bits
    return uint256_to_32bytes_be(n)   # always starts with 0x00
```

— <https://docs.world.org/world-id/idkit/signatures.md>. Implementation on disk agrees exactly
(`node_modules/.pnpm/@worldcoin+idkit-core@4.3.0/node_modules/@worldcoin/idkit-core/dist/hashing.js`):
`keccak_256`, `BigInt("0x"+hex) >> 8n`, `padStart(64, "0")`, returned as `"0x" + bytesToHex(...)`.

Encoding rules that bite:

- **Input encoding is conditional.** A `Uint8Array` is used as-is; a string that starts with `0x` *and* is valid even-length hex is **decoded as bytes**; anything else is UTF-8 encoded. (`isValidHex` requires non-empty, even length, `[0-9a-fA-F]` only.) So `"0xabcd"` and the literal 6 characters `0xabcd` hash differently. Rust matches: "`Signal::from_string` intentionally mirrors JS `hashSignal`, including decoding valid `0x` strings as bytes so address signals match `abi.encodePacked(address)`" — <https://raw.githubusercontent.com/worldcoin/idkit/main/rust/core/src/bridge.rs>.
- **Output is lowercase**, `0x`-prefixed, 64 hex chars, and the leading byte is always `00` (the `>> 8`). The Portal's validator is case-strict on the way in: `/^0x[\dabcdef]+$/` — an uppercase `signal_hash` is rejected as "Invalid signal_hash." (<https://raw.githubusercontent.com/worldcoin/developer-portal/main/web/api/v4/verify/request-schema.ts>). Nullifiers, by contrast, accept `/^(0x)?[\da-fA-F]+$/`.
- Test vectors to check a reimplementation against: `""` → `0x00c5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a4`; `"test_signal"` → `0x00c1636e0a961a3045054c4d61374422c31a95846b8442f0927ad2ff1d6112ed`; `[0x01,0x02,0x03]` → `0x00f1885eda54b7a053318cd41e2093220dab15d65381b1157a3633a83bfd5c92`; `"hello"` → `0x001c8aff950685c2ed4bc3174f3472287b56d9517b9c948127319a09a7a36dea`. — <https://docs.world.org/world-id/idkit/signatures.md>

`hashSignal` is exported for exactly this purpose: `import { hashSignal } from "@worldcoin/idkit-core/hashing"`
— pure JS, no WASM init, so it is Worker-safe (`…/idkit-core/README.md`, "Subpath Exports").

## Q7. Rate limits and operational notes

- **Documented rate limits on the verify API: none — Not found in primary sources.** A grep of the entire docs corpus (<https://docs.world.org/llms-full.txt>) for *rate limit / 429 / too many requests* returns one unrelated hit: a `429 RATE_LIMIT_EXCEEDED` on a credential-refresh endpoint. Neither <https://docs.world.org/api-reference/developer-portal/verify.md> nor the OpenAPI spec declares a 429 response. A code search of `worldcoin/developer-portal` finds rate limiting only in `web/api/helpers/rate-limit.ts`, referenced by `web/api/mcp/index.ts` — **not** by `web/api/v4/verify`. (The MCP `upload_app_image` tool documents 60/min, 500/day — that is image upload, not verification.) **Edge/CDN-level limits are Unknown.** Do not build a burst-heavy flow on the assumption that none exists.
- **Cap on verifications per action: exists for legacy cloud actions, not in the v4 path.** `max_verifications` — "Maximum number of verifications allowed for this action", default **1** — is a field on legacy incognito actions (<https://docs.world.org/api-reference/developer-portal/create-incognito-action.md>), and `max_verifications_reached` — "Action already verified the maximum allowed number of times. Treat as terminal business-rule outcome." — is a live IDKit error code (<https://docs.world.org/world-id/idkit/error-codes.md>). But `max_verifications` appears **nowhere** under `web/api/v4` (code search: 0 hits), and the v4 `create_world_id_action` MCP tool takes only `app_id`, `action`, `description`, `environment` — no cap parameter (<https://raw.githubusercontent.com/worldcoin/developer-portal/main/web/api/mcp/SKILL.md>). Whether a v4-created action inherits a default cap is **Unknown**. Because the default for legacy actions is 1, an `orbLegacy` flow against a Portal action created the legacy way could plausibly return `max_verifications_reached` on a second attempt — which is harmless for fuda (it wants one badge per human anyway) but must be handled as a distinct, non-error outcome.
- **A separate `…-test` action is supported — confirmed, and it is the officially recommended pattern.** "If the user needs both simulator testing and real-device QA, **create separate staging and production actions**." and "Use **separate actions** for separate one-time operations." — <https://docs.world.org/world-id/SKILL.md>. Nullifier isolation follows from Q3: a different `action` changes the external nullifier (3.0) / the OPRF input (4.0), so a tester who burns a nullifier on `…-test` still has an unused nullifier for the production action. fuda's plan is correct.
- **Side effects of a test action: one, and it is benign.** The v4 verify endpoint **auto-creates an unknown action** on first successful verification — "If action doesn't exist, create it with the resolved environment" (`CreateActionV4` with `rp_id`, `action`, `description`, `environment`) — <https://raw.githubusercontent.com/worldcoin/developer-portal/main/web/api/v4/verify/uniqueness-proof/handler.ts>. So a `…-test` action needs no pre-registration to be verified. Two caveats: (a) it will appear in the Portal afterwards, and (b) **World App may still precheck the action before generating a legacy 3.0 proof** — the documented symptom is "World ID shows 'action not found' or QR scan does nothing → Action wasn't created in the environment IDKit is pointing at" (<https://docs.world.org/world-id/SKILL.md>), and `/api/v1/precheck/{app_id}` returns 400 "No action found for this app." (<https://docs.world.org/api-reference/developer-portal/get-action-metadata.md>). Whether that precheck runs for a 4.0-RP legacy request is **Unknown**. **Create the test action in the Portal before the demo rather than relying on auto-creation** — it costs nothing and removes a class of silent failure.
- **`action_description` is a legitimate on-the-fly hint:** "The description of the specific action (shown to users in World App). Only recommended for actions created on-the-fly." — shipped `.d.ts`.

## Cross-cutting risks for the badge feature

1. **`environment` in the verify *response* echoes the request body.** The handler returns `environment: requestedEnvironment` — the client-supplied value. Asserting `response.environment === "production"` in the Worker (as <https://docs.world.org/world-id/idkit/integrate.md> Step 5 instructs) is correct and necessary, but it is a check against a value the prover influenced; the server-side guarantee is the staging-access gate of Q1. Keep the assertion; do not mistake it for the whole defence. Also assert `protocol_version` and `action` match what the Worker asked for.
2. **`allow_legacy_proofs: true` + a 4.0-capable preset would break one-human-one-badge.** The shipped type says it outright: "`true`: Accept both v3 and v4 proofs. Use during migration. **You must track both v3 and v4 nullifiers to prevent double-claims.**" (`…/idkit-core/dist/index.d.ts`), and the migration guide's contract example checks old *and* new nullifier maps. The same human can hold a v3 nullifier and a distinct v4 nullifier for the same action. **fuda is safe only because `orbLegacy` is 3.0-only.** The `(verifier, scope, subject_key)` index does **not** protect against this — the scope string is identical while the subject keys differ. Switching to `proofOfHuman` is not a drop-in change; it is a uniqueness-model change.
3. **Scope semantics shift between protocol versions.** 3.0 nullifiers are scoped to `app_id` + `action` (`generateExternalNullifier(appId, action)`); 4.0 nullifiers are scoped to `rp_id` + `action` ("derived from (user, rpId, action)"). `scope = app_id:action` is right today. If a 4.0 proof is ever accepted, the scope key should record which it is.
4. **Nonce hygiene.** `duplicate_nonce` — "RP reused a signature nonce. Generate a fresh nonce and signed RP context for **each request**." (<https://docs.world.org/world-id/idkit/error-codes.md>). One `signRequest` call per verification attempt; never cache the RP context. Default TTL is 300 s (<https://docs.world.org/world-id/idkit/signatures.md>), so a slow user hits `rp_signature_expired` — plan a re-sign path.
5. **Terminal vs retryable errors.** `world_id_3_not_available`, `credential_unavailable` and the version-availability family are terminal for that user and request; retrying is pointless. `inclusion_proof_pending` is retryable. — <https://docs.world.org/world-id/idkit/error-codes.md>
